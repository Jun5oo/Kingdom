# 카드 효과 시스템 명세

> 최종 목표: 로컬 서버 기반 카드 게임. 한 PC에서 서버 파일을 실행하고, 다른 PC의 클라이언트가 접속한다.
> 이번 단계 목표: 네트워크 없이도 효과 시스템이 정상 동작하되, 서버로 옮길 수 있는 구조로 만든다.

---

## 1. 전체 구조

### 1.1 서버 권위 + 이벤트 재생
- 규칙 판정은 **서버(엔진)에서만** 일어난다.
- 클라이언트는 **명령을 보내고**, **결과 이벤트를 받아 재생**만 한다. 클라이언트는 규칙을 몰라도 된다.
- 락스텝(양쪽이 같은 엔진 실행) 방식은 쓰지 않는다.

### 1.2 서버 형태
- **1단계 (현재):** Unity Dedicated Server 빌드. 카드 데이터는 JSON과 Lua 파일(§5.7)이라 서버와 클라이언트가 같은 파일을 읽는다.
- **최종 단계:** 순수 .NET 콘솔 서버로 옮긴다. 카드 폴더(JSON, Lua)는 그대로 쓰고, 규칙 코드는 공유 DLL로 만든다.
- 이번 단계에는 네트워크 전송 계층을 만들지 않는다.

### 1.3 규칙 코드 제약 (.NET 서버 이전 대비)
- 규칙 코드(State, Engine, Effect)는 **별도 asmdef**로 분리한다. EditMode 테스트 asmdef가 이 asmdef를 참조한다.
- 규칙 asmdef는 **Unity 참조를 끈다**(`noEngineReferences`). Unity 타입을 쓰면 컴파일러가 막는다.
  - 좌표는 `Vector2Int` 대신 자체 타입 `GridPos`를 쓴다.
  - 로그가 필요해지면 `Debug.Log` 대신 주입받는 인터페이스로 남긴다.
  - 난수는 시드 기반 RNG를 쓴다.
  - 카드 정의는 JSON과 Lua(§5.7)에서 읽는다. 그림 같은 Unity 자원은 클라이언트 쪽에만 둔다.
  - 외부 의존은 Newtonsoft Json과 MoonSharp(순수 C# Lua 인터프리터)만 허용한다. .NET 서버에서도 같은 라이브러리를 쓴다.
- 규칙 로직에서는 async/await와 코루틴을 쓰지 않는다. 입력 대기는 데이터 상태로 표현한다(§2.3).
- 엔티티는 **ID로 참조**한다(유닛, 플레이어, 카드). 효과 계층이 객체 참조를 들고 있지 않는다.

## 2. 엔진 입구

### 2.1 조회: `GetAvailableCommands(playerId)`
- 지금 가능한 수를 모두 돌려준다. 예: `유닛5: 이동 [칸들] / 공격 [대상들] / 효과① 발동`.
- UI는 이 목록으로만 버튼, 메뉴, 강조 표시를 그린다. 마스터 듀얼에서 카드를 누르면 "소환 / 효과 발동" 메뉴가 뜨는 것과 같다.

### 2.2 실행: `Submit(playerId, command) → 이벤트 목록`
- 이동, 공격, 턴 종료, 소환, 효과 발동, 선택 응답, 킹 배치를 **모두 같은 입구**로 받는다.
- 엔진은 입력이 필요해지거나 할 일이 없어질 때까지 진행한 뒤, 그동안 생긴 이벤트를 돌려준다.
- 클라이언트가 조작된 명령을 보내도 `Submit`이 다시 검증한다.
- 기존 `MoveUnit`, `AttackUnit` 같은 개별 메서드는 이 구조로 옮긴다.

### 2.3 선택 대기 (해결 도중 입력)
- 엔진이 입력을 기다릴 때는 "선택 대기" 상태를 데이터로 저장한다. 내용은 누가 고르는지, 후보 목록, 고를 개수다.
- 선택 응답이 `Submit`으로 들어오면 저장된 상태에서 해결을 이어간다.
- 시간 초과와 접속 끊김 처리는 네트워크 단계에서 정한다.

### 2.4 예시: 명령과 이벤트의 흐름
```
클라이언트 → Submit(P1, 효과발동{유닛5, 효과①})
엔진      ← 선택 대기{"상대 영웅 선택", 후보=[유닛9, 유닛12]}
클라이언트 → Submit(P1, 선택{유닛12})
엔진      ← [피해 유닛12 -10] [피해 유닛13 -10] [사망 유닛13]
            [자원 +1 (사망 트리거)] → 대기 상태로 복귀
```

## 3. 숨겨진 정보와 이벤트 공개 범위
- 손패와 덱은 숨겨진 정보다.
- 모든 이벤트에 **공개 범위**가 있다: 전체 공개, 또는 특정 플레이어에게만 공개.
- 플레이어별로 이벤트를 거르는 필터 함수를 이번 단계에서 만들고 테스트로 검증한다.
  - 예: 드로우를 하면 본인은 카드 내용을 받고, 상대는 "1장 뽑음"만 받는다.

## 4. 효과 해결 규칙 (하스스톤식)

### 4.1 대응 없음
- 상대 턴에 카드를 내서 끼어드는 대응(체인, 스택)은 없다. 효과는 순서대로 처리한다.
- 기존 `ResetFlag.OnChainEnd`는 제거한다.

### 4.2 트리거 순서
- 동시에 발동한 트리거는 **유닛이 필드에 나온 순서**로 해결한다. 순서 기준은 생성 순으로 증가하는 유닛 ID다.
- 부활한 유닛은 새 ID를 받으므로 가장 나중 순서가 된다.
- 해결 중에 새로 생긴 트리거는 진행 중인 효과에 끼어들지 않고 **큐 뒤에** 붙는다.
  - 실제 하스스톤은 새 트리거를 먼저 처리(깊이 우선)하지만, 구현과 예측이 쉬운 큐 뒤 방식을 유지한다.
- 큐에서 기다리는 동안 보드를 떠난 유닛의 트리거는 발동하지 않는다. 자기 자신의 사망에 반응하는 트리거는 예외다.

### 4.3 사망 처리
- HP가 0이 되어도 즉시 제거하지 않는다.
- 진행 중인 효과가 끝나면 사망자를 **한꺼번에** 처리하고 사망 트리거를 큐에 넣는다. 새 사망자가 없을 때까지 반복한다.
  - "끝나면"은 트리거 큐가 **모두 빈 뒤**를 뜻한다(하스스톤의 Death Creation Step).
  - 사망자를 모두 제거한 뒤 사망 이벤트를 낸다. 함께 죽은 유닛끼리는 서로의 사망에 반응하지 않고, 자기 자신의 사망 트리거는 발동한다.
- 희생(코드 이름 `Release`)은 예외다. 플레이어가 자리를 비우는 행동이므로 즉시 보드에서 제거한다. 사망 이벤트는 즉시 발생하고, 트리거는 §4.2대로 큐 뒤에 붙는다.
- 사망 이벤트에는 원인을 담는다: 피해, 파괴, 희생, 처형(처형은 값만 미리 둔다).
- 현재 `AttackUnit` 흐름의 즉시 제거 방식은 이 구조로 바꾼다.

### 4.4 대상이 없을 때
- **사용 시점:** 유효한 대상이 없으면 그 효과를 사용할 수 없다. 비용도 지불하지 않는다.
  - 예: 아군 무덤이 없으면 부활 효과 버튼이 비활성화된다.
- **해결 도중:** 후보가 0개이거나 대상이 사라졌으면 그 Operation만 건너뛰고 다음으로 진행한다. 이미 지불한 비용은 돌려주지 않는다.
  - 예: "폰 카드 1장을 뽑고, 손패 1장을 버린다"에서 덱에 폰이 없으면 뽑기를 건너뛴다. 손패도 0장이면 버리기도 건너뛴다.

## 5. 효과 데이터 구조

### 5.1 네 슬롯 유지 + 변경점
| 슬롯 | 역할 | 변경 |
|---|---|---|
| Condition | 사용 또는 발동 가능 여부 | **발동 이벤트 내용을 읽을 수 있게** 한다(누가 죽었는지, 누가 죽였는지). 별도의 트리거 필터는 두지 않는다. |
| Cost | 비용 확인과 지불 | 유지 |
| Target | 대상 결정 (자동 또는 플레이어 선택) | 유지. 범위 패턴을 지원한다(§5.4). |
| Operation | 실제 효과 | Lua 함수 하나. 여러 동작을 순서대로 적는다. |

- 트리거는 `EffectData`의 "발동 이벤트 종류" 항목 하나로 둔다.
- 횟수 제한은 턴당 횟수(`usesPerTurn`)만 지원한다. 게임당 제한은 필요한 카드가 생기면 기준(유닛, 카드 이름 등)을 정해 추가한다.
- 저작은 카드별 Lua 파일로 한다(§5.7). Condition, Target, Operation은 Lua 함수이고, 발동 방식·횟수·Cost는 Lua 값이다.

### 5.2 효과 종류
| 종류 | 설명 | 예 |
|---|---|---|
| 기동 | 플레이어가 비용을 내고 사용한다 | 자기희생, 부활, 범위 공격 |
| 트리거 | 이벤트가 생기면 발동한다 | 사망 시, 턴 시작 시 |
| 지속 | 저장된 값을 고치지 않고, 조회할 때마다 수정치를 합산한다 | 내 유닛 공격력 +1 |

- **기본값은 효과가 고치지 않는다.** 하스스톤처럼 모든 변화를 유닛에 붙는 상태 이상(하스스톤의 강화효과)으로 남긴다. 그래야 침묵 같은 효과가 상태 이상을 떼는 것만으로 정확히 원래대로 되돌릴 수 있다. 받은 피해(`CurrentHP`)는 변화가 아니라 결과이므로 예외다.
- CP 조회 값 = 카드 기본값 + 유닛에 붙은 상태 이상의 수치 합 + 지속 효과 수정치(6단계).
  | 효과 | 분류 | 이유 |
  |---|---|---|
  | 주변 아군 공격력 +1 (오라 유닛이 있는 동안) | 지속 효과 | 위치에 따라 계속 바뀐다. 상태 이상으로 붙이면 이동·사망·소환마다 동기화가 필요하다. |
  | 공격력 +3 (영구), 2턴 동안 공격력 +1 | 상태 이상 `{ cp = … }` | 건 순간에 대상이 정해진다. 침묵으로 뗄 수 있다. |
  | 내 턴마다 공격력 +1 (영구 성장) | 트리거가 턴마다 상태 이상 `{ cp = 1 }`을 하나씩 붙인다 | 누적값을 상태 이상 개수로 남기므로 침묵으로 되돌릴 수 있다. |
- 범용 대체 효과는 만들지 않는다. 필요한 카드가 생길 때마다 해당 처리 단계에 확인 지점을 추가한다.
  - 첫 사례는 피해 처리 단계에서 보호막(`Shield`) 상태 이상을 확인하는 지점이다.

### 5.3 상태 이상 (버프, 디버프)
한글 용어는 "상태 이상"으로 써서 런타임 상태(State)와 구별한다. 코드 이름은 클래스 `Status`, 종류 enum `StatusType`이다. 하스스톤의 강화효과에 해당한다.

`UnitState`가 상태 이상 목록을 가진다. 유닛이 보드를 떠나면 함께 사라진다. 각 상태 이상의 정보는 다음과 같다.
- 종류(`Type`, 선택): C# 확인 지점이 있는 키워드일 때만 둔다. 동작 이름으로 짓고 카드 이름으로 짓지 않는다(하스스톤 키워드처럼). 예: `Shield`
- 수치(6단계): `cp` 등. 조회할 때 합산한다.
- 남은 턴 수: `null`이면 영구다. **유닛의 현재 주인**의 턴이 시작될 때마다 1씩 줄고, 0이 되면 만료된다.
- 상태 이상을 건 플레이어, 건 카드 ID(화면 표시용)
- 만료 시 실행할 Lua 함수(`onExpire`): **턴 만료 때만** 실행한다. 보호막 소모나 해제로 사라질 때는 실행하지 않는다.

```lua
ctx:addStatus(unitId, { type = 'Shield', turns = 2 })                                  -- 키워드
ctx:addStatus(unitId, { cp = 3 })                                                      -- 수치 (6단계)
ctx:addStatus(unitId, { turns = 2, onExpire = function(ctx) ctx:destroy(ctx.sourceUnitId) end })  -- 지연 효과
```

규칙
- **같은 유닛에 여러 개가 쌓인다.** 교체하지 않는다. 다른 카드가 건 지연 효과끼리 덮어쓰지 않고, 성장 효과가 누적된다.
- 키워드는 그 종류의 상태 이상이 하나라도 있으면 적용된다.
- C# 동작은 종류마다 해당 처리 단계의 확인 지점에 둔다(§5.2). 확인 지점은 가상 메서드로 만들지 않는다.
- 추가 데이터나 제거 시 정리가 필요한 종류만 `Status`를 상속한다. 예: 매혹(`CharmedStatus`)은 돌아갈 주인을 가지고, 어떤 이유로 제거되든 `OnRemoved`에서 주인을 되돌린다.
  - 원래 주인이 매혹된 자기 유닛을 매혹하면 기존 매혹을 모두 풀고 새로 걸지 않는다.
- 상태 이상 제거는 한 메서드를 거친다(만료, 보호막 소모, 해제 모두). 제거할 때 `OnRemoved`는 실행하고 `onExpire`는 실행하지 않는다.
- `Shield`(하스스톤의 천상의 보호막): 피해 처리 단계에서 0보다 큰 피해 1회를 0으로 만든다. 이때 그 유닛의 `Shield`를 **모두** 제거한다. 겹쳐 걸어도 1회만 막는다. 피해가 0이면 소모되지 않는다.
- 아무 동작도 없는 상태 이상(종류, 수치, `onExpire`가 모두 없음)이나 `onExpire`는 있는데 남은 턴 수가 없는 상태 이상은 실행 때 예외다.
- 파괴(`ctx:destroy`)는 피해 처리 단계를 거치지 않고 사망 일괄 처리에서 원인 `Destroy`로 처리한다. 그래서 피해를 막는 상태 이상은 파괴를 막지 못한다.
- 침묵(이후 작업)은 유닛의 상태 이상을 모두 제거하고, 그 유닛 자신의 카드 효과(트리거, 기동, 지속)를 끄는 표시를 남기는 것으로 구현한다.

이후 추가 후보(카드가 생길 때 종류 하나와 확인 지점 하나씩 추가): `Rooted`(이동 불가), `Disarmed`(일반 공격 불가), `Charmed`(주인 변경), `Taunt`, `Stealth`, `Elusive`, `Poisonous`, `Reborn`, `Immune`, 침묵.

### 5.4 범위 패턴
- 효과마다 **중심 칸으로부터의 오프셋 목록**으로 적는다. 예: 상하좌우 1칸 = `(0,1) (0,-1) (1,0) (-1,0)`.
- 오프셋은 **보드 절대 좌표**로 적고, 효과 주인에 따라 뒤집지 않는다. 지금 범위는 모두 위아래 대칭이라 뒤집어도 결과가 같기 때문이다.
- "전방"처럼 방향이 있는 범위가 필요해지면, 그때 플레이어 2의 오프셋 y 부호를 바꾸는 처리를 추가한다. 카드 데이터 형식은 바뀌지 않는다.

### 5.5 능력 자원
- 플레이어당 값 하나(`AbilityResource`)를 둔다. 한 덱은 단일 종족이다.
- 표시 이름만 종족별로 다르다: 언데드는 데스카운트, 천상은 여신 카운트.

### 5.6 작성 예시
부활 카드:
```
EffectData
  종류:      기동
  횟수 제한: 턴당 1회
  Condition: 아군 무덤 1개 이상
  Cost:      능력 자원 2
  Target:    플레이어가 아군 무덤 1개 선택
  Operations:
    1. 대상 희생
    2. 그 칸에 무덤의 원래 유닛 소환
```
사망 트리거 카드:
```
EffectData
  종류:       트리거 (발동 이벤트 = 유닛 사망)
  Condition:  죽은 유닛 = 상대 영웅 AND 죽인 쪽 = 나
  Operations: 1. 능력 자원 +1
```

### 5.7 카드 데이터 (JSON + Lua)
YGOPro처럼 수치는 데이터 파일에, 효과는 카드별 스크립트에 둔다.

- **파일:** 카드 한 장 = JSON 파일 하나 + (효과가 있으면) **같은 이름의** Lua 파일 하나. 위치는 `Assets/StreamingAssets/Cards/`이다. 빌드할 때 원본 그대로 복사되어 클라이언트와 서버가 같은 파일을 읽는다.
  - JSON: id, 이름, 종족, 분류, 레벨, 수치·이동·공격 범위. 카드 하나에 레벨 하나다(§6.4).
  - Lua: 효과 목록 `{ 효과, ... }`을 return 한다.
- **효과 테이블 항목:** `type`(Ignition/Trigger/Continuous), `trigger`, `usesPerTurn`, `cost = { abilityResource, actionResource }`, `condition(ctx)`, `target(ctx)` + `targetCount`, `operation(ctx, targets)`. 모르는 항목은 로딩 오류다.
- **ctx:** 스크립트는 `LuaEffectApi`의 public 멤버로만 엔진에 접근한다. 상태 변경은 모두 `Processor`를 거친다. `condition`과 `target`에서 상태를 바꾸려 하면 예외가 난다.
  - 새 동작이 필요하면 `LuaEffectApi`에 메서드를 추가한다. 자주 쓰는 복잡한 동작(예: 범위 피해)도 C#에 두고 스크립트는 호출만 한다.
- **샌드박스:** Lua 파일·OS 모듈을 뺀 `Preset_HardSandbox`로 실행한다.
- **다형성(JSON):** 이동 규칙은 `"type"` 값으로 C# 클래스를 고른다. 이름과 클래스의 대응은 `CardLoader` 등록표 한 곳에서 관리한다. Newtonsoft의 `$type`은 쓰지 않는다(어셈블리 이름이 데이터에 박히고, 임의의 클래스를 만들 수 있는 보안 문제).
- **읽기:** 규칙 코드의 `CardLoader`가 폴더 또는 (파일 이름, 내용) 목록을 받아 `CardDefinition`을 만든다. 폴더 경로는 호출하는 쪽(Unity 또는 서버)이 정한다.
- **검증:** 로딩할 때 JSON의 모르는 `type`·빠진 항목·잘못된 수치, Lua의 문법 오류·모르는 항목·짝 없는 Lua 파일을 검사한다. 오류에는 파일 이름과 위치를 담는다. 중복 ID는 `CardDatabase`가 검사한다.
  - Lua는 실행 전에는 내용을 알 수 없으므로, 소환할 카드가 있는지 같은 검사는 실행 때 예외로 드러난다. 스크립트 실행 오류는 파일 이름과 줄 위치를 담은 `InvalidOperationException`이다.
- **그림:** 카드 그림은 데이터에 넣지 않는다. 클라이언트가 카드 ID로 찾는다.

## 6. 게임 요소 추가

### 6.1 영역과 카드
- 손패, 덱, 묘지 영역과 "손패에서 소환" 명령을 추가한다.
- 이번 단계는 **유닛 카드만** 다룬다. 카드를 내는 흐름은 `카드를 냄 → (유닛이면) 소환 → 냈을 때 트리거` 순서다. 이렇게 두면 나중에 주문 카드를 끼울 수 있다.

### 6.2 기물 타입
- 카드에 `기물 타입` 항목(폰, 나이트, 비숍, 룩, 퀸)을 추가한다. 종족, `UnitTag`와는 별개다.
- 덱 제한은 타입별 합계로 센다: 폰 8, 나이트 2, 비숍 2, 룩 2, 퀸 1. 서로 다른 나이트 카드를 섞어도 합쳐서 2장까지다.
- 이동 규칙은 카드 데이터가 정한다. 기물 타입은 분류와 효과 조건에 쓴다. 예: "나이트 카드를 뽑는다", "상대 나이트 1장을 봉쇄한다".

### 6.3 킹
- 킹은 덱에 넣지 않는다.
- 게임 시작 시 **배치 단계**를 둔다. 선공부터 번갈아 자기 진영 맨 뒷줄의 원하는 칸에 킹을 놓는다.
- 배치도 `GetAvailableCommands`와 `Submit` 흐름으로 처리한다.

### 6.4 레벨
- 합성(레벨업)은 없다. 레벨은 카드마다 고정된 기물 등급이다: 폰 1, 비숍·룩·나이트 2, 퀸 3.
- 레벨은 효과가 카드를 찾는 조건으로 쓴다. 예: "레벨 2 카드를 가져온다". 조회 함수는 덱·패를 만들 때(7단계) `LuaEffectApi`에 추가한다.

## 9. 현재 코드에서 바꿔야 할 점 (조사 결과)
- `Operation`에 실행 메서드가 없고, 효과를 실행하는 곳(`Processor`)도 없다. `UnitLevelData.Effects`를 읽는 코드도 없다.
- `EffectContext.Targets`는 `List<Vector2Int>`인데 `Amount.Resolve`는 `UnitState`를 받는다. 대상 표현을 통일해야 한다.
- `GameEvent`가 객체 참조(`TriggerCard`, `ReasonEffect`)를 쓴다. ID로 바꾼다.
- State에 손패, 덱, 묘지, 상태 목록, 승패가 없다. `nextUnitId`가 State가 아니라 Engine에 있다.
- asmdef가 없어서 전부 `Assembly-CSharp`에 들어간다.
- 카드가 ScriptableObject(`UnitCardData`)와 `SerializeReference`로 저장되어 있다. `pawn.asset`과 `knight.asset`을 JSON으로 옮기고 에셋은 삭제한다.
- Presenter가 엔진 메서드를 직접 부르고 상태를 다시 읽는다. 이벤트를 재생하는 방식으로 바꾼다.
- 옛 카드와 효과 데이터(`Assets/CSV`, `AbilityTable.csv`)는 작업 트리에서 삭제되어 git 히스토리에만 남아 있다.

## 10. 구현 순서
장 번호는 주제별로 나눈 것이고 구현 순서가 아니다. 구현은 의존 관계 순서로 진행한다. 각 단계가 끝날 때 **기존 게임이 동작하고 테스트가 통과하는 상태**를 유지한다.

### 10.1 1부: 효과 시스템 (이번 범위, 네트워크 없음)
| 단계 | 내용 | 관련 장 | 완료 확인 | 상태 |
|---|---|---|---|---|
| 0 | 규칙 asmdef 분리(Unity 참조 차단), 테스트 asmdef, `GridPos`, 카드 JSON 읽기와 검증, 기존 카드 2장 JSON 이전 | 1.3, 5.7, 9 | 기존 게임이 그대로 동작하고, 카드 JSON 로딩 테스트가 통과함 | 완료 |
| 1 | 엔진 입구: 명령 타입, `Submit`, `GetAvailableCommands`, ID 기반 이벤트 목록(공개 범위 포함), 사망자 일괄 처리. 이동, 공격, 턴 종료를 이 구조로 옮기고 Presenter를 이벤트 재생 방식으로 변경 | 2, 4.3 | 이동, 공격, 사망, 턴 종료 테스트 | 완료 |
| 2 | 효과 실행 핵심: `Operation` 실행, 트리거 큐(필드에 나온 순서), 희생, 이벤트를 읽는 Condition | 4.2, 4.3, 5.1, 5.2 | 카드 ① 사망 트리거, ② 자기희생 | 완료 |
| 3 | 비용, 선택 대기, Operation 목록 | 2.3, 4.4 | 카드 ③ 부활 | 완료 |
| 4 | 범위 패턴(보드 절대 좌표) | 5.4 | 카드 ⑥ 범위 공격 | 완료 |
| 5 | 상태, 피해 처리 단계의 확인 지점 | 5.3 | 카드 ④ 지연 파괴, ⑦ 보호막 | 완료 |
| 6 | 지속 효과(수정치 합산), 상태 이상 수치(`cp`), CP를 저장값 대신 계산값으로 변경 | 5.2, 5.3 | 카드 ⑤ 공격력 오라 | 다음 |
| 7 | 손패, 덱, 묘지, 소환 명령, 기물 타입, 킹 배치 단계, 이벤트 공개 범위와 플레이어별 필터 | 3, 6 | 드로우 공개 범위 테스트, 배치 단계 테스트 | |

- **0단계가 먼저인 이유:** asmdef가 없으면 EditMode 테스트를 만들 수 없다.
- **1단계가 중요한 이유:** 효과도 "명령 → 이벤트" 흐름 위에서 동작하기 때문이다. 이 단계의 `Submit`과 이벤트 목록이 그대로 네트워크 프로토콜이 된다.
- **`Processor` 이름과 수명:** 효과뿐 아니라 공격, 이동, 턴 종료까지 한 명령의 해결을 맡으므로 `EffectProcessor`는 실제 역할보다 좁아 `Processor`로 바꿨다. 3단계 후 Submit마다 만들던 방식을 바꿔, `GameEngine`이 하나를 만들어 게임 내내 쓴다(YGOPro, Forge처럼 처리기가 게임과 함께 산다). 이벤트는 처리기 안에 쌓고 Submit이 끝날 때 `TakeEvents`로 꺼낸다. 꺼낼 때 목록을 새것으로 바꿔 이전 결과가 다음 Submit과 섞이지 않게 한다. 클래스 분리는 하지 않았다.
- **효과 저작을 JSON 부품에서 Lua로 바꾼 이유 (4단계 후):** 카드 게임은 규칙을 깨는 카드가 많아 부품 조합만으로는 부품 클래스가 계속 늘어난다. YGOPro(Lua), Legends of Runeterra(Python)처럼 효과를 카드별 스크립트로 적고, 엔진 API(`LuaEffectApi`)로 할 수 있는 일을 제한한다. 수치는 계속 JSON에 둔다(§5.7).
- **7단계를 마지막에 두는 이유:** 효과 시스템과 비교적 독립적이라 다른 단계를 막지 않는다. 다만 이벤트의 공개 범위 항목은 1단계부터 이벤트에 넣어 둔다.

### 10.2 2부: 네트워크 (효과 시스템 완료 후)
| 단계 | 내용 | 상태 |
|---|---|---|
| 8 | 메시지 형식: 명령, 이벤트, 선택 대기, 가능한 수 목록을 직렬화한다. 직렬화하고 다시 읽어도 같은 결과가 나오는지 테스트한다. | |
| 9 | 전송 계층: 서버가 LAN에서 접속을 받고, 클라이언트가 IP로 접속한다. 클라이언트 쪽 `Submit`은 네트워크 호출로 교체하고, 화면 코드는 바꾸지 않는다. | |
| 10 | 서버가 이벤트를 보내기 전에 플레이어별 필터를 적용한다. 숨겨진 정보가 상대에게 새지 않는지 테스트한다. | |
| 11 | Unity Dedicated Server 빌드: 서버 실행 파일 하나와 클라이언트 두 개로 실제 대전을 한다. | |
| 12 | 접속 끊김, 재접속, 선택 대기 시간 초과를 처리한다. | |
| 13 | 순수 .NET 서버로 이전한다. 카드 폴더(JSON, Lua)를 그대로 쓰고, 규칙 asmdef를 공유 DLL로 만든다. | |

- 전송 방식(직접 만든 TCP 소켓 또는 Unity Transport)은 8단계를 시작할 때 정한다. 13단계(.NET 이전)를 고려하면 Unity에 묶이지 않는 방식이 유리하다.

### 10.3 그 외 이후 작업
- 처형 이동 (8장)
- 덱빌딩 화면과 덱 검증 (6.2)
- 주문 카드 (6.1)
